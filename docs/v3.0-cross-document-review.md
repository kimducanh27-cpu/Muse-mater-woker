## Critical findings and dispositions

### P0-1 — Security gate was policy-only / not wired

**Before:** The Phase 2 and Phase 3 execution flows dispatched two reviewers (UX/visual and code/architecture) but no mandatory Security Reviewer. Master aggregation did not require a security artifact or define an unoverrideable security veto.

**Change made:** Added `SECURITY_REVIEW.md`; appended normative dispatch and evidence requirements to Phase 2, Phase 3, and Master. The required artifact is `.agy/security-review.json`, bound to exact base/head SHAs. Security FAIL/BLOCKED blocks integration, merge, release, and final PASS. Security Reviewer is read-only and independent.

**Remaining runtime work:** Implement actual fresh-context dispatch, read-only permissions, scanner/tool integration, artifact schema validation, exact-SHA validation, and required CI status checks. Until these exist, this gate is contractually required but not proven executable.

### P0-2 — Phase 3 remediation reran only E2E/review

**Before:** Phase 3 Step 6 directed remediation to rerun Step 4 (E2E) and Step 5 (review), omitting build, typecheck/compile, lint, unit/state matrix, visual recapture, component immutability, and responsive checks.

**Change made:** Added a mandatory 12-part full regression matrix to Phase 3. Every code/configuration change invalidates all previous evidence. Reviewers cannot be dispatched until regression is complete. ARBITRATION remains pending, not PASS.

**Remaining runtime work:** Implement commands/evidence adapters per Web and Android target; run the matrix in CI; add negative tests proving missing/stale evidence cannot pass.

### P1 — Central `REVIEW.md` missing

The file does not exist on the inspected default branch. Therefore the previously described taxonomy, diff-focused scope, duplicate suppression, convergence limits, known-bug/clean-patch evaluation, and false-positive/false-negative metrics cannot be treated as current repository policy. Create it in a separate, evidence-led change after the P0 runtime wiring. Do not invent evaluation targets before building and measuring a corpus.

### P1 — Token linter is fail-open and absent

Phase 2's embedded sample uses `|| true` around a grep pipeline, which can suppress command errors and turn missing/unavailable checks into apparent success. The referenced `scripts/lint-tokens.sh` itself is absent. This linter is a design-token/style constraint tool, not a secret scanner. Replace the sample with explicit required-directory/tool checks and nonzero failure behavior; implement separate secret, dependency, static security, authorization, and network/mock checks.

### P1 — Accessibility criteria need exact WCAG mapping

Phase 1 describes all semantic interactive color pairs as requiring 4.5:1 and groups 3:1 for large text/UI components. This overgeneralizes the criteria. WCAG 2.1 AA text contrast is 4.5:1 for normal text and 3:1 for large text (SC 1.4.3). Non-text UI component boundaries/states and graphical objects are evaluated under SC 1.4.11 at 3:1 against adjacent colors where applicable. Do not apply either threshold indiscriminately to every color pair. Update Phase 1 and the audit implementation against the normative WCAG criteria before claiming compliance.

### P1 — One canonical state vocabulary is not yet fully propagated

The Master addendum defines `NOT_RUN/PASS/FAIL/BLOCKED/ARBITRATION/FLAKY`, but Phase 2 and Phase 3 legacy prompts still use binary `[PASS]/[REJECT]`. Keep reviewer verdicts as findings if needed, but map them deterministically into the canonical gate state. Do not allow a legacy PASS/REJECT string to bypass BLOCKED, ARBITRATION, or FLAKY.

### P1 — Rollback and orchestration implementation remain unverified

The Master document contains illustrative shell fragments and conflicting timeout statements (three-minute heartbeat timeout and ten-minute timeout). It does not provide verified executable state-transition tests, crash-recovery tests, merge-lease protection, or a complete durable evidence lifecycle. These require implementation and negative tests; this document review does not claim they work.

## v3.0 gate vocabulary

- `NOT_RUN`: required gate has not executed.
- `PASS`: all applicable checks passed with complete, current evidence.
- `FAIL`: a check failed or a blocking finding remains.
- `BLOCKED`: required input, dispatch, tool, evidence, or approval is missing/invalid.
- `ARBITRATION`: evidence is complete and a human decision is pending; never merge-eligible.
- `FLAKY`: nondeterministic result; not PASS and release-blocking until resolved or handled by an explicitly authorized policy.

Missing, malformed, stale, skipped, unsupported, or unconfigured required checks are BLOCKED, not PASS.
