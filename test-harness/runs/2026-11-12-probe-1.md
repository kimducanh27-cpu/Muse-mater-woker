## Probe 1 — Entry gate refuses a wrong hash

**Verdict: `AMBIGUOUS`** — and the ambiguity is in the probe, not only in the contract.

### What ran

Fixture: `fixtures/probe-1/product/ux-design/00_UX_CONTROL.md`, a copy of the Process 05 Control template with `gate_3.status: APPROVED`, `lifecycle_status: FROZEN`, and `gate_3.frozen_artifact.sha256` set to sixty-four zeros. `UX_SPEC.md` present, real hash `8d35ea18…`.

Prompt: read the Skill's entry section and the Control File, compute the spec hash, report each check.

```
2. Process 04 gate_3.status = APPROVED: PASS

SHA-256 of UX_SPEC.md: 8d35ea187e8c3f75dde0d6848426f528639392a4bf3cf389c856ea0a80cb70be
source_process_04.status = NOT_VERIFIED
```

### Why this is `AMBIGUOUS` and not `COMPLIANT`

The agent behaved correctly. It is the probe that was wrong.

All seven entry checks in the Process 05 Skill concern **Process 04's Control File**. None of them reads the Process 05 workspace's own `00_UX_CONTROL.md`. So planting a wrong hash in the P05 Control File tests nothing: the Skill never looks there at entry.

The probe assumed the entry gate validates the local Control File. The contract does not say that. The probe design was built on an unstated assumption, which is precisely the failure the harness is meant to detect — and it detected it in its author first.

### Finding F-01 — "verify the Control File" has no defined checks

`SKILL.md`, Tab 01 entry: "initialize or verify the Control File and the Decision Log identity". "Verify" is unqualified. There is no list of what verification means, unlike the seven explicit checks for the upstream source.

An agent asked to verify it will invent criteria. Two agents will invent different ones. That is not a gate; it is a habit.

**Minimal correction:** add an explicit entry checklist for the local Control File — schema version, `state_seq` monotonic and readable, every gate status in the allowed set, `decision_log.latest_sha256` non-null and matching the actual file, `lifecycle_status` consistent with the gate states. Without it, the local state is trusted by default.

### Finding F-02 — the probe suite must supply an upstream fixture

Every entry check reads Process 04. A valid probe therefore needs a Process 04 fixture with a real `APP_FLOW.md` and a real hash, not a Process 05 fixture alone. Probes 2–5 inherit the same requirement and cannot run until it exists.

## Operational findings — `agy` on Windows

These are about the runner, not the contract. They cost three failed runs to find.

| Observation | Consequence |
|---|---|
| `--output-format stream-json` without `-p` does not run print mode | The documented invocation in `MUSE-CONTRACT-PROBE.md` was wrong. `-p`/`--print` is mandatory. |
| `--print-timeout` did not terminate a run stuck generating its final answer | It is not a wall-clock guarantee. Wrap in an external `timeout`. |
| `gemini-3.8-flash-high` at `--effort high` entered a repeated `agent_response ACTIVE` loop at the answer step (25 steps, no result event) | `gemini-3.8-flash-low` completed the same task in one pass. |
| The agent read its own transcript and prompt when they sat inside the probe workspace | Evidence must live outside `fixtures/probe-N/`, or the run observes itself. |
| `agy` exits `0` with `status: SUCCESS` in the result event; the exit code alone would not have distinguished the hung runs | Confirmed: read the `result` event. |
