# v3.0 Cross-Document Consistency and Enforcement Review

**Baseline:** `main` at `ada4241117b13cbd35c9e03f88894bf9c23a449c`  
**Working branch:** `v3.0-p0-gate-enforcement`

## Baseline verification

The inspected baseline contained `README.md`, `MUSE_ORCHESTRATOR.md`, and `docs/specs/phase-1.md`, `phase-2.md`, `phase-3.md`. `REVIEW.md` and `SECURITY_REVIEW.md` were absent at repository root and under `docs/`. The repository also had no checked-in `scripts/lint-tokens.sh`, gate validator, `.github/workflows/ci.yml`, or `security.yml`. The baseline commit reported no combined CI statuses. These are repository facts, not claims about uncommitted files or external runtime configuration.

## P0-1 — Security review was not wired into the pipeline

**Baseline evidence:** the Orchestrator's `.agy/last-run.json` example contained only Vision and Code reviewer results, and Master merged when `status == PASS`. Phase 2 and Phase 3 each dispatched two non-security reviewers and committed after their consensus. No `SECURITY_REVIEW.md`, security artifact, security dispatch step, or security aggregation gate was present.

**Branch changes:** created `SECURITY_REVIEW.md` as the authoritative security policy and `REVIEW.md` as the shared gate/evidence policy. The Phase 2, Phase 3, and Orchestrator addenda require a fresh-context, read-only Security Reviewer for every code candidate. The report is bound to the exact candidate SHA at `.agy/runs/<run-id>/security-review.json`. Missing evidence, a failed scan, an unresolved finding, stale SHA, reviewer mutation, or any non-PASS security state blocks checkpoint/merge/release. Master arbitration cannot override the security veto.

**Owner:** Worker remediates; independent Security Reviewer owns the security verdict; Master dispatches and enforces; human owner handles escalation and risk approvals.

## P0-2 — Phase 3 remediation omitted full regression

**Baseline evidence:** Phase 3 Step 6 reran Step 4 E2E, then Step 5 reviewers. It did not require build, typecheck, lint, unit tests, state-matrix tests, visual snapshot verification, component immutability, and complete responsive/platform checks. Phase 2 Step 7 also reran snapshot capture and reviewers only; the handoff's claim that Phase 2 already had a stronger full-regression-after-remediation gate was not supported by the live file.

**Branch changes:** `REVIEW.md` defines one platform-aware full-regression contract for both code-producing phases. Phase 2 and Phase 3 addenda require that contract after every code edit, including remediation. Only after regression passes may the Master dispatch fresh independent reviewers and a fresh Security Reviewer.

## Canonical execution sequence

`DISPATCHED → EXECUTING → CANDIDATE_READY → REGRESSION → INDEPENDENT_REVIEW + SECURITY_REVIEW → AGGREGATING → CHECKPOINTED`

On remediation:

`FAIL/REJECT → REMEDIATING → new candidate SHA → complete REGRESSION → fresh independent reviews + fresh SECURITY_REVIEW → AGGREGATING`

`BLOCKED`, `ARBITRATION`, and `FLAKY` remain non-eligible. Any source change invalidates every previous candidate-bound report.

## Unresolved P1 items — deliberately outside the P0 patch

1. **WCAG contrast matrix:** Phase 1 uses 4.5:1 too broadly for all text/icon pairs and 3:1 too broadly for all borders/icons. WCAG 2.1 SC 1.4.3 sets 4.5:1 for normal text, 3:1 for large text, with exceptions. SC 1.4.11 sets 3:1 for visual information required to identify UI components/states and meaningful graphical objects against adjacent colors—not every border or icon. Reconcile by element and context. Sources: [W3C SC 1.4.3](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html), [W3C SC 1.4.11](https://www.w3.org/WAI/WCAG21/understanding/non-text-contrast.html).
2. **Token linter:** the script is only embedded in Phase 2 prose and is not present as a repository file. Its ERE includes a lookbehind and its `|| true`/directory handling can fail open. Add tested coverage for `rgb()/hsl()`, missing directories, and portable grep behavior in a separate P1 change.
3. **Risk policy:** defect severity (P0/P1/P2) and change risk (LOW/MEDIUM/HIGH) are distinct. A dedicated machine-readable policy is still needed for changed paths, data sensitivity, privilege boundaries, blast radius, and release impact. Medium/high-risk human approval remains mandatory; AI agents never count as humans.
4. **FLAKY:** baseline has no explicit release policy for `FLAKY_WARNING`. This v3 policy treats FLAKY as non-eligible; retry/waiver details remain to be specified.
5. **Reviewer evaluation:** define known-bug, clean-patch, regression, and false-positive datasets and measurement methods before selecting quality targets.
6. **Rollback:** the cited `git revert -m 1` instruction from the handoff was not found in the inspected baseline files, so it could not be verified against this repository version. If added later, document its merge-commit-only mainline-parent semantics.
7. **CI/runtime enforcement:** no baseline workflow or status check existed. The validator and tests on this branch do not prove remote CI, branch protection, Muse runtime dispatch, or production Web/Android execution.
8. **Orchestrator recovery:** heartbeat and crash-recovery behavior remain prose-level contracts; no executable supervisor has been verified in the repository.
