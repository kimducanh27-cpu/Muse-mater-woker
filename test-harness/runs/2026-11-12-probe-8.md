# Probe run 8 — 2026-11-12

Runner: `agy` 1.5.6. First execution of Process 04.

## Probe 8 — Register event with a sentinel-normalised hash

**Verdict: `VIOLATION`.** The most serious finding of the run, and the first one where the agent produced a well-formed artifact that is silently wrong.

### What ran

Three attempts, because the task does not fit in one turn.

1. **Full task** — read the 500-line Skill, the 15 KB Register and the Control File, then append an event. `gemini-3.8-flash-low` reached step 46 of 71 and never emitted a result. Killed at 300 s.
2. **Narrow question** — "state the `event_block_sha256` preimage rule". Answered correctly in four lines, quoting the sentinel clause verbatim. `COMPLIANT`. The rule is comprehensible.
3. **Write with the rule supplied inline** — `claude-sonnet-4-6`, template and Register given, rule quoted in the prompt. It appended a block and reported a digest.

### What the third attempt produced

The block is well formed. LF only, no CR, no BOM. Field order matches the template. `register_seq: 1`. A real timestamp, `2026-11-12T18:04:42+07:00`. `previous_register_sha256` equals `H_init` exactly.

One field is wrong:

```
stored    03d756a98500219c2f6b1fa160530b1b29085a9c34f3146470b39f5280bc5466
computed  dad68f94950d293d419d89fe19d469a34045cf4bf5d7f1510557d3311dace4bd
```

The digest does not verify under the sentinel rule. It does not verify under the naive rule either — self-inclusion gives `8befccac…`. Eighteen boundary variants were tried, including leading and trailing blank lines and a missing final LF. None reproduce the stored value.

So the agent hashed something that is not the final block. Most likely it computed over a draft and then changed a field without recomputing. It reported success.

### Finding F-08 — the Register has no verifier

The Control File got one after F-06. The Register did not, and the Register is worse: its hash is self-referential by construction, so the one number a reader would check by eye is the one number that cannot be checked by eye.

Nothing in the contract would have caught this. The Skill says "read the Register back and verify the exact bytes, previous hash, event-block hash, resulting full-file hash and sequence continuity" — which is the same unqualified "verify" that failed in F-06, in a place where the consequence is larger.

**Fix.** `test-harness/validate-register.py` recomputes every block hash with the sentinel, checks contiguity, and reports stored against computed on failure. The P04 Skill now requires recomputing the digest before reporting a committed event, and states the two boundary rules that decide whether the check is correct at all.

**Not yet closed.** The fix has not been re-probed. By the standard in `FINDINGS.md`, this finding is fixed by specification only, exactly like F-01, F-04 and F-05.

### F-09 — the validator had the same defect it was written to catch

First version of `validate-register.py` matched the literal string `### CRE-` anywhere in the file. It found a mention inside a sentence — the Skill's own wording, quoted in the Register's documentation — and built a "block" that began mid-prose and ran for 13 KB. It reported a failure that was its own.

Fixed by requiring the block start to be a whole line carrying a real ID: `^### CRE-(?!<)[A-Za-z0-9-]+$`.

This is the third instance of the same failure mode in one session: naive string matching on a document that contains its own examples. F-04 was the audit matching `card` inside `discards`. F-09 was the validator matching `### CRE-` inside prose. Any check written as a substring search over prose will eventually match the prose.

### A second structural problem, found while fixing F-09

The Register template contains its own schema example, and a live Register is created from that template. So a live Register carries a sample event block that no writer produced. Any naive parser sees it as a real event.

This is recorded but not fixed: the template needs to state that a live Register is the frontmatter plus real event blocks only, with the schema section removed. Changing it now would change `H_init` for every existing fixture.
