## F-10 — the banned list collides with the workflow's own vocabulary

Found by running the validator, not by reading it.

First run against a correct artifact:

```
FAIL  component audit: line ~3 matched 'tab' — "Owner: Tab 01."
```

`Tab 01` is a process role. `tab` is a banned UI affordance. With case-insensitive whole-word matching they are the same token.

Every artifact 01 carries `Owner: Tab 01` in its header, so **the audit as written fails every correct artifact on its first line**. That is precisely the failure F-04 predicted in the abstract, now demonstrated on a clean file.

**Fix.** Exclude `Tab <n>` and `TAB_<n>` before matching, in both the validator and the Skill's procedure. The exception is required, not optional, and it is written down as such.

This is the fourth substring-family defect of the session, and the first one that would have failed a *correct* artifact every single time.

## F-01 is not closed, and the reason matters

Tab 01 entry now enumerates six Control File checks. Probe 10's transcript contains **zero** occurrences of `state_seq`, `schema_version`, `decision_log` or `lifecycle`. The agent read the Skill, produced the artifact, ran the validator and reported.

It never performed the six checks. Nothing in its acceptance condition required them.

**F-11 — writing a checklist does not make it run.** The checks exist in the Skill and were skipped, because the visible deliverable was the artifact and the validator only covered the artifact. Whatever is not in the acceptance condition is optional, regardless of how firmly it is worded.

This is the same lesson as F-06 and F-08 from the other direction: those were fixed by putting a check in the loop, this is a demonstration of what happens when the check stays in the prose.

**Not fixed.** The fix is not another paragraph. It is either a Control File validator the agent must run before producing anything, or an acceptance condition that requires the six results in the output. Both are larger than this turn.
